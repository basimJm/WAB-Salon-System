## 0. How to Read This Document

- **MUST** = mandatory requirement. **SHOULD** = strongly recommended. **MAY** = optional.
- Every screen section contains: purpose, entry points, layout (top to bottom), behavior, states, and acceptance criteria.
- Anything not decided is listed in **Section 17 – Open Items & Assumptions**. Do NOT invent behavior for open items; implement the stated assumption and keep it easy to change.
- "Start" / "End" refer to layout direction: in Arabic (RTL) Start = right, End = left; in English (LTR) Start = left, End = right. **Never hardcode left/right.**
- All user-visible strings MUST be localized (Arabic + English). No hardcoded text.
- **Words:** "business" = salon, clinic or tattoo studio. "Salon" is used only where a rule is really salon-only. API, route and field names stay as in the contract (`salonId`, `GET /salons`, `SalonCard`) for every business type.
- A line starting **"Not built yet:"** marks a place where today's app differs from the stated rule.

## 1. Product Overview

### 1.1 Summary
**WAB Wedding & Beauty** is a marketplace mobile app (Android + iOS) that lets customers in **Jordan** discover **businesses of three types: salons (men, women or both), beauty clinics and tattoo studios**, browse their branches, services, staff, reviews, working hours and portfolio, and **book appointments** for themselves and up to 5 companions. Salons serving women support **bride bookings** with VIP services and bride-qualified staff; tattoo studios accept one optional design image per person. The designed payment options are pay on arrival, deposit or full online; online payment is paused today, so the app offers pay on arrival (Section 2.1).

### 1.2 Actors in the Whole System
| Actor | Description | Covered here |
|---|---|---|
| Customer (Guest) | Uses the app without an account | ✅ |
| Customer (Registered) | Has an account, can book, review, favorite | ✅ |
| Merchant (Business) | Owner and team of a salon, clinic or tattoo studio: profile, branches, services, staff, bookings | ❌ (Merchant PRD) |
| Admin | Manages platform, content, approvals | ❌ (Admin PRD) |

### 1.3 Market Constraints
- Country: Jordan (phone input still supports a server-provided country list).
- Currency: **Jordanian Dinar (JOD) only**. All prices are **tax- and fee-inclusive** (the business includes them when entering prices). The app never adds taxes or fees.
- Languages: **Arabic (default)** and English.

## 2. Platform & Technical Constraints

### 2.1 Confirmed
- **Kotlin Multiplatform (KMP) + Compose Multiplatform.** Shared UI **and** shared business logic for **Android and iOS**. Platform-specific code only via `expect/actual` where unavoidable (location, payments SDK, video player, image picker, push, deep links).
- **Local persistence:** DataStore (key-value). See Section 5.
- **OTP:** phone code generated by **the backend** and delivered **on WhatsApp by ARQAM OTP** (BUSINESS_DOMAIN §3.1a). The backend verifies the code and answers a single-use `otpToken` (see S13). No Firebase Phone Auth, no SMS fallback, no direct Meta Cloud API.
- **Push notifications:** Firebase Cloud Messaging (Android + iOS), one Firebase project per environment.
- **Real-time:** Socket.IO client connected to the backend while the app is in the foreground (registered users); FCM covers background/closed app.
- **Crash reporting & analytics:** Firebase Crashlytics + Firebase Analytics (see Section 14). Firebase serves push, analytics and crash reporting only.
- **Internal abstraction (mandatory):** all Firebase usages MUST sit behind interfaces in the app's own code (`PushTokenProvider`, `AnalyticsBackend`, `CrashReporter`, `AppInstanceIdProvider` in `core/firebase`) so a provider change touches one place only. No separate repositories for these on mobile.
- **Payments:** designed through the **`wab-payments` KMP library** (published package). The app depends only on its interface; changing the gateway MUST NOT require app code changes beyond the library version. **Status today: online payment is paused.** No gateway is chosen (HyperPay is only a candidate), the server runs `PAYMENT_PROVIDER=disabled` in production and `fake` in dev, and the app does not include the library yet. The app offers pay on arrival and shows online payment as "coming soon".
- **Files:** uploads use **presigned upload URLs** issued by the backend and go directly to object storage: **Cloudflare R2** (`STORAGE_PROVIDER=cloudflare-r2`, public + private bucket; AWS S3 + CDN is only a fallback). Images and videos MUST be **compressed on the device** before upload.
- **Backend (context only):** Node.js + TypeScript + Express + Mongoose, MongoDB, Redis. REST JSON APIs under the customer namespace `/customer/v1`. The contract is the generated `WAB-Server/docs/api/openapi.customer.json` (+ Postman); the app regenerates its DTOs from it.

### 2.2 Tech Stack
Stack and module map: `WAB-Mobile-Customer/TECHSTACK.md` and `WAB-Mobile-Customer/CLAUDE.md` §2. Integrations confirmed in 2.1 are fixed.

### 2.3 Environments
- Two environments, **Dev** and **Prod**, each with its own base URL, configured at build time. The hosted dev API is on Render (`wab-server-dev.onrender.com`). Production hosting and the platform domain are open owner decisions (Section 17).

## 3. Global Rules (apply to every screen)

### 3.1 Localization & Direction
- Default language: **Arabic**. Supported: Arabic, English.
- Full **RTL** layout in Arabic; mirrored **LTR** in English (icons with direction, e.g., back arrows, MUST mirror).
- Numerals follow the active language.
- Time format: **12-hour** with AM/PM (Arabic: ص / م).
- Language can be changed from: Profile screen, Login screen, Register screen. Change applies immediately and is persisted locally.
- Every API request MUST send the current language (e.g., `Accept-Language: ar|en`) so the server returns localized content.

### 3.2 Theme
- Options: Light / Dark / System. **Default: System.**
- Can be changed from Profile, Login and Register screens. Persisted locally.

### 3.3 Loading
- All loading states use **shimmer placeholders shaped like the real content** (cards, sections, list items).
- **Home uses one unified loading state on its first load**: one request and one shimmer layout that mirrors all sections. Near you then keeps its own placeholder until a position arrives; Home never waits for location. Switching the type lens keeps the shown sections and adds a small loading indicator.

### 3.4 Pagination
- All lists that come from the server are **paginated, page size = 10**, with infinite scroll (load next page when reaching the end) and a bottom loading indicator (shimmer item).
- Applies to: Search (S04), All Services, Reviews (business/staff), Notifications, Bookings, Favorites, filter services list ("See more" loads next 10).

### 3.5 Search Debounce
- Every search input MUST debounce: send the request only after the user stops typing for **500 ms**. Never request per keystroke.

### 3.6 Pull to Refresh
- **Every screen supports pull-to-refresh EXCEPT form screens**: Login, Register, OTP, Edit Personal Information, and all Booking Flow steps.

### 3.7 Error & Empty States
Every data screen MUST handle:
| State | UI |
|---|---|
| No internet | Illustration + message + **Retry** button |
| Server / unknown error | Illustration + message + **Retry** button |
| Empty result | Illustration + contextual message (+ action when defined) |

### 3.8 Horizontal Sections & "See more / See all"
- Home horizontal sections show a title at Start and a **"See more"/"See all"** action at End.
- Each section holds 10 items; the action is shown **only when the server says there are more** (`hasMore`).

### 3.9 Truncated Text
- Long descriptions (service, business, reviews, staff bio) are truncated with a **"more"** action that expands or navigates as specified per screen.

### 3.10 Business Types, Audience and Discovery
Rules: BUSINESS_DOMAIN §5.19, §5.22, §5.23.
- Every business has a **`businessType`** (`SALON`, `CLINIC`, `TATTOO`; never changes) and an **`audience`** (`MALE`, `FEMALE`, `BOTH`). A salon serves men, women or both; clinics and tattoo studios are always `BOTH`.
- **Gender never filters discovery.** Gender is asked only in guest setup (S02) and registration (S12). Home, Near you, Recommended, favorites, deep links and search list every customer-visible business of every type and audience for everyone. The stored gender only selects the banners (`gender` on `GET /home`).
- **Type lens:** chips **All · Salons · Clinics · Tattoo** (default All) on Home, Search and Bookings. On Home the lens filters every section at once.
- Every business card shows its **type label + audience** ("Salon · Women", "Beauty clinic · Men & women").
- A men's or women's salon stays visible to everyone but only takes persons of its audience (`GENDER_MISMATCH`, S16). Gender also exists as an optional search filter in S05: Men = audience `MALE` or `BOTH`, Women = `FEMALE` or `BOTH`.
- **Customer-visible business** = `state = LIVE`, complete, with at least one bookable branch (BUSINESS_DOMAIN §5.2).

### 3.11 Server-Driven Content
The following are **never hardcoded**; they come from the server:
- Countries list (flag, name, dial code, phone regex).
- Cities and areas.
- Filter data: catalog services (per business type) and price range bounds. The general filters (Nearest, Recommended) and the 1★–5★ rating scale are fixed in the app.
- Banners, Recommended businesses, nearby radius.
- Legal and support content: Privacy Policy, Terms & Conditions, About Us, FAQ, Contact information (phone, WhatsApp, email).
- App version policy (force/optional update) and maintenance mode.
- OTP code length and resend timing.

### 3.12 Auth-Gated Actions
When a **Guest** triggers an action requiring an account, show a dialog: "You need to log in to continue" with **Log in** (→ Login screen) and **Cancel**. Auth-gated actions:
- Book (business details "Book" button).
- Add review (business or staff).
- Add/remove favorite.
- Open Favorites tab content.
- Notifications (icon is not shown for guests).

### 3.13 Relative Time Format
- "Now", "X minutes ago", "X hours ago", "Yesterday / 1 day ago", "2 days ago"; **older than 2 days → full date**.

### 3.14 Images
- All images are loaded from URLs (public storage or CDN) with caching and placeholders. Missing profile images show a default vector avatar.

### 3.15 Real-time
- For registered users, the app keeps an authenticated **Socket.IO** connection while in the foreground and reconnects automatically.
- Real-time updates MUST be applied to: Bookings list (S14), Booking Details (S15), unread notifications badge (S03) and Notifications list (S19).
- When the app returns to the foreground or receives an FCM message, it refreshes the affected data.

### 3.16 Uploads
- Flow: request presigned URL from backend (`POST /uploads/presign`: purpose, file type, size) → compress on device → upload directly to storage → confirm upload to backend (`POST /uploads/confirm`) → backend returns the final URL.
- Customer purposes: `CUSTOMER_AVATAR` (profile photo) and `BOOKING_REFERENCE` (tattoo design image, private bucket). Private files are shown only through short-lived signed URLs.
- Show upload progress and allow retry on failure.

### 3.17 Branches
Rules: BUSINESS_DOMAIN §5.2, §5.11, §5.16–§5.18.
- A business has **one or more branches** (limit `salon.maxBranches`, default 20).
- **Per branch:** location, contacts, hours, closures, services and prices, staff (each staff member belongs to one branch).
- **Business-wide:** name, audience, logo, cover, gallery, description, policy, rating, Recommended placement.
- A branch is **bookable** when the business is customer-visible and the branch is `ACTIVE` and complete. Offline and closed branches are not shown to customers; upcoming bookings of an offline branch or business are kept.
- **Search lists one card per business** (the nearest bookable branch gives distance and area; no location = main branch; "· N branches" when several). **Near you lists one entry per bookable branch**, named "Business - Branch" when the business has several, the business name alone when it has one.
- Favorites, banners and deep links point at the business; a deep link may carry `branchId` to preselect a branch.
- Reviews and the rating are business-wide; a review shows its branch as a label only.
- Booking notifications name the place "Business - Branch" when the business has more than one non-closed branch.

## 4. App Launch & User State Machine

### 4.1 User States
| State | Condition |
|---|---|
| New device | No `onboarding_seen` flag |
| Guest (incomplete) | No access token AND guest nickname/gender not saved |
| Guest (complete) | No access token AND guest nickname + gender saved |
| Registered | Valid access token saved |

### 4.2 Launch Decision Flow
```
App start
 ├─ Check app version policy / maintenance (server)
 │    ├─ Maintenance → Maintenance screen (blocking)
 │    ├─ Force update → Force Update screen (blocking)
 │    └─ Optional update → show dismissible update dialog, continue
 ├─ onboarding_seen == false → Onboarding (set onboarding_seen = true as soon as it is shown)
 ├─ Has access token → Home (Registered)
 ├─ Guest nickname + gender saved → Home (Guest)
 └─ Else → Nickname & Gender screen (mandatory) → Home (Guest)
```

### 4.3 Rules
- **Onboarding** is shown **only on the very first launch after install**. Once displayed, it is considered seen even if the user exits mid-way. Reinstalling the app shows it again.
- **Nickname & Gender screen** is shown on **every launch** until the user completes it. The user cannot reach Home without saving both.
- Registered users **never** see the Nickname & Gender screen.
- After registration/login, the guest nickname and gender are **kept** locally (not deleted).
- **Session:** access token + refresh token. Refresh MUST be automatic and transparent. Only if refresh fails: show "Session expired" message, clear registered-user data (tokens, first name, gender), and continue as Guest (if guest nickname/gender are missing → Nickname & Gender screen; user can log in again from anywhere).

### 4.4 Deep Links
- Business share link format (platform domain open, Section 17; the dev host is the hosted dev API): `https://<domain>/salon/{salonId}`, with optional `?branchId={branchId}` to preselect a branch (Android App Links + iOS Universal Links). The same path serves every business type.
- On open:
  1. If the user must pass onboarding / nickname & gender → complete those first.
  2. Open Home, then automatically push **Business Details** (S07) for `salonId`.
  3. Back from Business Details returns to Home.
- If the business does not exist or is not customer-visible → open Home and show a "not available" message.
- Not built yet: the message reads "Salon not available" for every business type.

**Entry:** First launch only.

- Skip or finishing → S02 (or Home if already completed).

- Not built yet: the first page's text names only men's and women's salons, not clinics or tattoo studios.
**Acceptance criteria:**
- [ ] Shown on first launch after install only.
- [ ] Not shown again after app restart even if the user quit mid-onboarding.

### S02 — Nickname & Gender
**Purpose:** Personalize the guest experience: a nickname for the welcome message and a gender that selects banners and prefills registration. Gender never filters discovery (Section 3.10).
**Entry:** After onboarding, and on every launch until completed.
**Layout:**
- Nickname text field (required).
- Gender selection: Man / Woman (required).
- Continue button (disabled until both are valid).
**Behavior:**
- Saves `guest_nickname` and `guest_gender` **on the device**; no account is created (what leaves the device: Section 15).

- [ ] If the app is closed before completing, this screen appears again on next launch.

### S03 — Home
**Purpose:** Discovery entry point across every business type.
**Entry:** Bottom nav "Home" (default tab).
**Data loading:** One request, `GET /home`, with the stored `gender` (selects banners only), the lens as `businessType` (none = All) and `lat`/`lng` when a position is known. It returns banners, Explore, Near you, Recommended, and for registered users Book again and the unread notifications count. Home sends it at once and never waits for a position. Unified shimmer on the first load.

**On-screen order (top → bottom):** Header (item 1) → Search bar (3) → Type lens (4) → Banners (2) → Explore (5) → Recommended (6) → Book again (8) → **Near you (7), always last** (BUSINESS_DOMAIN §5.22). Item numbers are stable references cited by code and backlogs. An empty Banners, Explore, Recommended or Book again section is left out; Near you always shows.

**Item 1 — Header row**
- Start: the line "What would you like to book today?" over the welcome message — Guest: "Hello, {guest_nickname}"; Registered: "Hello, {user_first_name}" (first name only).
- End (registered only): **Notifications icon** with unread badge. Badge shows 1–99, then "99+". Hidden when 0. Updates in real time. Tap → S19.
- Not built yet: no location line in the Home header.

**Item 3 — Search bar (non-editable)** — hint: "Search salons, clinics, tattoo studios or services". Tap → S04 with **no filters**, empty search and the lens on All.

**Item 4 — Type lens:** chips **All · Salons · Clinics · Tattoo** (default All).
- Selecting a chip reloads every section for that type; the shown sections stay, with a small loading indicator, until the answer arrives.
- There is no gender control on Home.

**Item 2 — Banner carousel** — auto-swiping images (ads/promotions/upcoming features), chosen by the stored gender. Tap behavior by `actionType`: `SALON` → S07, `EXTERNAL_URL` → open in browser, `NONE` → nothing. Managed by Admin.

**Item 5 — Explore** — title "Explore" (Start), "See more" (End, only with `hasMore`).
- The most-booked catalog services across the lens' types. Horizontal tiles: image, type label, name, short description (truncated).
- Tap → S04 pre-filtered by that service, with the lens on that service's type.
- "See more" → S06 with the same lens.

**Item 6 — Recommended** — title + "See all" (only with `hasMore`).

### S13 — OTP Verification (shared)
**Used by modes:** LOGIN, REGISTER, CHANGE_PHONE, BOOKING_CONFIRMATION.
**Layout:** Title, message "We sent a code to {phone}", **code input with N boxes** where **N = `otpLength` returned by the backend (currently 6)** — never hardcoded, **Verify** button, resend control with countdown.

**Flow (WhatsApp OTP, BUSINESS_DOMAIN §3.1a):**
1. App calls backend **OTP request** (phone, purpose). Backend checks platform limits, generates the code, has ARQAM OTP deliver it **on WhatsApp** (AR/EN template by `Accept-Language`) and returns `{ allowed, otpLength, resendAfterSeconds, expiresInSeconds, blockedUntil? }`. Message: "We sent a code on WhatsApp to {phone}".
2. User enters the code → app calls backend **OTP verify** (phone, purpose, code) → single-use **`otpToken`**.
3. App sends the `otpToken` to the action of that purpose (login / register / change phone / booking confirmation). A failed action needs a new code.

**Rules:**
- Channel: **WhatsApp** only (authentication template), no SMS fallback. A number without WhatsApp → "We couldn't send the code: this number has no WhatsApp account" (`OTP_DELIVERY_FAILED`), retry available.
- Resend becomes available after `resendAfterSeconds` (**60 s**), countdown shown; the code expiry (`expiresInSeconds`) is shown too.
- Expired code (`OTP_EXPIRED`, or the expiry countdown ends) → popup "This code has expired, please request a new one."
- **Send limit:** 5 requests within 5 minutes → blocked for **15 minutes** (show remaining time from `blockedUntil`).
- **Wrong attempts:** counted by the backend on verify; the wrong-code message shows the attempts left (server text); 5 wrong codes → blocked for **15 minutes** (`OTP_BLOCKED`).
**On success:**
- LOGIN / REGISTER → save tokens + user first name + gender → Home (no Nickname screen).
- CHANGE_PHONE → save profile changes → back to Profile.
- BOOKING_CONFIRMATION → continue booking flow (see S16).

### S16 — Booking Flow (multi-step, registered users only)
No pull-to-refresh. Show a step indicator. Back returns to the previous step preserving selections. The flow is the same for salons, clinics and tattoo studios. Step numbers are stable references cited by code and backlogs; the branch step comes before Step 0.

**Branch step (first; BUSINESS_DOMAIN §5.18)**
- Shown when the business has more than one bookable branch. With exactly one, that branch is auto-selected and the step does not exist.
- One selection card per branch, main first: name, address, today's open/closed line. Hint: "Services, prices, staff and times depend on the branch." Continue needs a branch.
- A branch chosen on S07 or carried by a deep link is already the answer: the flow opens on Step 0, and Back returns to this step.
- Every later step uses that branch only. Changing the branch clears services, staff and slots for every person (names and the bride flag stay). The draft and the booking keep `branchId`.

**Step 0 — Person setup (per person)**
- Main person name defaults to the account holder's name (editable). Companions require a name.
- **Gender per person (BUSINESS_DOMAIN §5.19):**
  - **Salon with audience MALE or FEMALE:** not asked. Every person is of the salon's audience; any other gender is refused (`GENDER_MISMATCH`). A customer of the other gender cannot book it for themselves (BUSINESS_DOMAIN §12 point 11).
  - **Salon with audience BOTH, every clinic, every tattoo studio:** required for each person (Man / Woman); one booking may mix genders. The main person is prefilled from the account's gender.
  - Not built yet: the app does not compare a men's or women's salon with the account holder's gender, so it never blocks a customer of the other gender from continuing.
- **Bride:** only at a salon with audience FEMALE or BOTH, never at a clinic or tattoo studio (`BRIDE_NOT_ALLOWED`). Toggle **"This person is a bride"** for a person whose gender is Woman; switching the person to Man clears it. More than one bride per booking is allowed. The account holder may book for a bride without receiving a service herself (e.g., a mother booking for her daughter — the main person simply represents the bride).
- **Design image (tattoo studios only, BUSINESS_DOMAIN §5.23):** one optional image per person. Pick → compressed on the device → uploaded as `BOOKING_REFERENCE` (Section 3.16) → preview with **Remove**. The key goes in `persons[].referenceImageKey`; the file is private and shown through short-lived signed URLs to the customer and to members who can view that booking. Any other business type → hidden (`BUSINESS_TYPE_MISMATCH`). There is no age check.
  - Not built yet: the image comes from the gallery only (no camera option).

**Step 1 — Select services**
- List of the services of the chosen branch (the business offers only services of its own type).
- **Multi-select.** Shows each service's price and duration, and the running **total price** and **total duration**.
- Services flagged **bride-only (VIP)** appear **only for persons marked as bride** (`BRIDE_ONLY_SERVICE`).
- Continue enabled when ≥1 service selected.

**Step 2 — Select date & time**
- Calendar from today up to **90 days** ahead.
- Days fully closed at the chosen branch (weekly day off or exceptional closure) are disabled.
- After selecting a date, show time slots at **15-minute intervals** within the branch's working hours.
- A slot is **available** if at least one staff member of the branch: is on duty that day, is not on leave, is qualified for **all** selected services (and **bride-qualified** if the person is a bride), and is free for the **entire total duration** starting at that slot (considering existing PENDING and APPROVED bookings).
- Unavailable slots are shown disabled with label **"Full"**.
- Slots already chosen for other persons in the same draft booking MUST be treated as occupied for that staff member (the server re-validates on submission).

**Step 3 — Select staff**
- Show **all** staff of the branch; eligible ones (per rules above for the chosen slot) are selectable, others shown **disabled**.
- Option **"Any available staff"** (the server assigns one).

**Step 4 — Companions**
- Prompt: **"Just me"** or **"Add companion"**.
- Up to **5 companions** (main + 5 = max 6 persons).
- Companions follow the Step 0 gender rule: of the salon's audience at a men's or women's salon, their own gender elsewhere.
- Each companion repeats Steps 0–3. Same staff at an overlapping time is not allowed; choose another time or another staff member.
- Persons can be removed from the draft before submission.

**Step 5 — Summary**
- Entering this step creates the server draft (`POST /bookings/drafts`): it validates everything, snapshots prices and the policy, and holds the slots for 10 minutes (`booking.paymentHoldMinutes`; expired = `DRAFT_EXPIRED`).
- Branch line ("Branch: {name}").
- For each person: name, bride badge, services + prices, staff, date/time.
- Grand total.
- **Business rules** block: cancellation window, deposit percentage, refund rules, the fact that the booking needs the business's approval.
- **Payment method selection** among the options enabled by the business: Pay on arrival / Deposit (shows deposit amount = total × percentage) / Full online payment.
- **Status today (online payment paused):** only Pay on arrival can be selected; Deposit and Full online show "Online payment coming soon" and are disabled. A business that offers no pay on arrival cannot be booked until online payment returns (`PAYMENT_OPTION_NOT_ALLOWED`).
- **Confirm** button.

**Step 6 — Verification & payment**
1. Confirm → OTP (S13, mode BOOKING_CONFIRMATION) to the user's phone.
2. If an online method was chosen → open the payment gateway (via the payment abstraction).
   - **Success** → booking is created with status **PENDING** → S17.
   - **Failure / cancelled** → booking is **not** created; return to Summary with an error message.
3. Pay on arrival → booking is created with status **PENDING** → S17.
- **Status today:** online payment is paused, so the flow is OTP → pay on arrival → PENDING.

**Refusals from the server** are shown as localized text by `code` (BUSINESS_DOMAIN §11), e.g., `GENDER_MISMATCH`, `TOO_MANY_COMPANIONS`, `BRANCH_NOT_BOOKABLE`, `SALON_NOT_BOOKABLE`, `SERVICE_UNAVAILABLE`, `STAFF_NOT_ELIGIBLE`, `SLOT_UNAVAILABLE`, `SLOT_TAKEN`.

**Acceptance criteria:**
- [ ] With several bookable branches the first step is the branch; every later step shows only that branch's services, staff and slots.
- [ ] Gender is asked per person only at BOTH salons, clinics and tattoo studios.
- [ ] The bride toggle exists only at FEMALE or BOTH salons, for a woman.
- [ ] The design image exists only at tattoo studios, optional, one per person.
- [ ] Online options are visible but disabled while online payment is paused.

**Business rules after creation** (see Section 9). Bookings the business makes for a customer do not use this flow (Section 9, rule 22).

## 9. Booking Business Rules (consolidated)

Rule numbers are stable references. Full rules: BUSINESS_DOMAIN §5.4–§5.10, §5.18–§5.23.

1. Only registered users can book in the app.
2. Total duration of a person's appointment = sum of selected services' durations. Slots every 15 minutes.
3. Staff eligibility: member of the chosen branch, on duty that day, not on leave, qualified for all selected services, bride-qualified if the person is a bride, free for the whole duration.
4. Weekly schedule can differ per day and per branch; **exceptional closures** of that branch override the weekly schedule.
5. Max booking horizon: **90 days**.
6. Max persons: main + **5 companions**. At a salon with audience MALE or FEMALE every person matches it (`GENDER_MISMATCH`); at a BOTH salon, clinic or tattoo studio persons may be any gender in one booking.
7. **Prices are locked at booking time** (later price changes do not affect existing bookings).
8. Every booking gets a **reference number** at creation.
9. A booking made in the app is **PENDING** until the business approves or rejects it. While PENDING, its slot/staff time is **held** — no other customer can book it.
10. Business rejects → `REJECTED` with a reason; if paid → **full refund**.
11. Business cancels an approved booking → `CANCELLED_BY_SALON` with a reason; **full refund** of anything paid (deposit or full).
12. **Auto-cancel:** if a booking is still PENDING **60 minutes after the appointment start time** (`booking.autoCancelAfterStartMinutes`), it becomes `AUTO_CANCELLED`; any payment is **refunded mandatorily**.
13. Customer cancellation:
    - PENDING booking → can cancel any time, **full refund**.
    - APPROVED booking → only before the business's cancellation window; refund per the snapshotted policy (deposit refundable or not; full payment refunded fully or minus deposit).
14. **No-show:** the business or admin marks `NO_SHOW`, at or after the start; deposit/payment handled per the snapshotted policy.
15. **Completion:** only the business (the assigned staff, a member with `BOOKINGS_OPERATE`, the owner) or admin marks `COMPLETED`, at or after the start. This enables rating. The customer sees it at once (socket + push).
16. Refunds are not instant: show `REFUND_PENDING` then `REFUNDED`; money returns to the original payment method. `REFUND_FAILED` is retried by the server and alerts the admin.
17. Deposit = business-defined **percentage** of the total.
18. The payment options available are those enabled by the business; the customer picks one. While online payment is paused, only pay on arrival can be picked.
19. **Branch:** every booking belongs to one bookable branch, chosen first when there are several; services, staff, hours and slots are that branch's.
20. **Bride:** only at a salon with audience FEMALE or BOTH (`BRIDE_NOT_ALLOWED`), for a woman; bride-only services only for a bride (`BRIDE_ONLY_SERVICE`).
21. **Tattoo design image:** one optional image per person at tattoo studios only (`BUSINESS_TYPE_MISMATCH` elsewhere); private; no age check.
22. **Bookings made by the business (BUSINESS_DOMAIN §5.20):** the owner or a member with `BOOKINGS_CREATE` enters a mobile number. A registered number links the booking to that account; it appears in S14 and S15 with "Booked by …" and every status notification names it. A number without an account stores contact details only: no account, **no WhatsApp or SMS**, and the booking is claimed automatically when that number registers. These bookings start `APPROVED`, pay on arrival, `source = MERCHANT`.
23. **Draft hold:** a draft holds its slots for 10 minutes (`booking.paymentHoldMinutes`). A failed payment never creates a booking.
24. **Closing:** an `APPROVED` booking past its end is closed by the business, reminded every hour until answered (BUSINESS_DOMAIN §5.21); the customer gets no closing reminder and sees the result at once.

## 14. Analytics & Monitoring
- **Firebase Crashlytics** for crashes and non-fatal errors.
- **Firebase Analytics**: track **every screen view and every user action** for both guests and registered users.
- The app does NOT send analytics events to the backend. The server records its own events in MongoDB (`serverEvents`) and the admin panel reads those. There is no BigQuery export and no `@wab/analytics` SDK in the server (owner decision 2026-10-19).

## 15. Security & Privacy
- The guest nickname never leaves the device.
- The stored gender (guest or registered) is sent only as the required `gender` parameter of `GET /home`, which selects banners, and as the `gender_scope` analytics field. A guest's value creates no account or profile.
- Recent searches stay on the device.
- Tokens stored securely; never logged.
- No personal data in URLs or analytics parameters beyond IDs and the above.
- Location is sent only when needed (Near you, Nearest) and only if permission is granted.
- Tattoo design images are private: presigned upload, private bucket, short-lived signed URLs, visible only to the customer and to members who can view that booking.
- Customer booking views show assigned staff as first name and photo only.
- A booking the business makes for a number without an account creates no account and sends no message to that number.
