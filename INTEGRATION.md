## 3. Contracts (the wire format every client builds against)
- **REST:** generated from server code, committed in `WAB-Server/docs/api/openapi.{common,customer,merchant,admin}.json` + Postman files (`npm run docs`, server `CLAUDE.md` §11). Operation counts today: customer 51, merchant 71, admin 116, common 3. Clients regenerate DTOs from the snapshot: admin `npm run api:sync` (ADM-004), customer/merchant `./gradlew apiSync` (CUS-009, MER-006). A server endpoint change = regenerate docs + name the affected client tasks in the server task block (`WAB_Server_Tasks.md` §1.10); the client task then runs its sync and fixes compile errors.
- **Envelope:** `{success, message, data, meta?}` / `{success:false, message, error:{code, details?, traceId}}`; clients branch on `code` (BUSINESS_DOMAIN §11), never on text. Every client keeps an AR + EN message per code (ADM-009, CUS-059, MER-052).
- **Socket.IO events and FCM payloads:** names and payloads in `BUSINESS_DOMAIN.md` §7; mirrored in `WAB-Server/src/constants`, admin `constants/realtime.ts`, customer/merchant realtime constants (CUS-013, MER-011). Admin today receives `booking.updated`, `alert.created`; SRV-124 adds the rest.
- **SDK ports:** the `WAB-Server/src/providers/<name>/types.ts` interfaces are the contract between the server and each SDK; an SDK adapter must satisfy them (`wab-notifications` does). Business rules never live in an SDK.
- **Auth:** phone + WhatsApp OTP for customers/members (server generates the code, ARQAM OTP delivers it over WhatsApp, `POST …/auth/otp/request` → `…/auth/otp/verify` → single-use `otpToken` for login/register/change phone/booking/bank details; BUSINESS_DOMAIN §3.1a), email + password + email OTP for admins; server JWT access (short) + rotating refresh per scope; a token of one scope never works on another namespace (root `CLAUDE.md` §4.2).

## 4. Working without the other side (mandatory)
1. **Never wait.** Build against the contract: fixtures per operation behind a repository interface, switched only by config (`VITE_DATA_SOURCE` admin, `DATA_SOURCE` apps, `*_PROVIDER=fake|real` server). Prod builds compile the mock out.
2. **Gaps are tasks, not guesses.** A client that needs something the contract lacks adds/asks for an `SRV-` row (Stage N = admin gaps, Stage O = merchant gaps) and marks its own row `BLOCKED` on it; `tasks.py set SRV-xxx DONE` flips it back to `TODO`.
3. **Status changes propagate both ways:** every task row lists its cross-project dependencies in *Needs* / *Server*; `scripts/tasks.py` updates dependents when a dependency is done and rebuilds §7. Changing a status by hand without the script is the only way to break the map — do not.

## 6. Definition of "integration ready" (per part) and release order
- Implements the current contract snapshot; DTO sync test green; every error code has AR + EN handling; mock and real behind one interface, switched by config; realtime and push payloads parsed with fixture tests; no hardcoded URLs or keys; dev and prod configs present.
- Order: production deployment (SRV-011) → SDK publish (SRV-112) → payments once a gateway is chosen (SRV-092) → end-to-end flows (booking request CUS→SRV→MER, payment, refund, push) → release tasks (CUS-066/067, MER-059/060, ADM-083).
